# qa-write-skill-istqb

QA를 위한 Claude 스킬입니다. 기획서(PRD)를 넣으면 ISTQB 테스트 설계 기법에 따라 테스트 케이스를 만들어 줍니다.

ISTQB(국제 소프트웨어 테스팅 자격 위원회)는 QA 자격증 기관이고, 이 스킬에 담긴 동등 분할, 경계값 분석, 결정 테이블, 상태 전이 같은 기법은 QA라면 반드시 알아야 하는 표준 기법입니다. 우리가 늘 머릿속으로 하던 "최솟값 바로 아래를 넣어 본다" 같은 생각에 붙은 공식 이름이기도 합니다.

## 왜 만들었나

테스트 케이스는 그동안 두 가지 방식으로 만들었습니다.

- **사람이 직접 떠올리기:** 시간과 노력이 많이 들고, 사람마다 결과가 달라집니다.
- **AI에게 기획서를 주고 "만들어 줘"라고 하기:** 빠르지만, 같은 기획서를 줘도 실행할 때마다 결과가 달라지고 무엇이 빠졌는지 알 수 없습니다.

그런데 프로덕트가 달라도 테스트 케이스는 비슷하게 반복됩니다. 반복되는 것은 규칙으로 만들 수 있고, 그 규칙이 바로 테스트 기법입니다. 이 스킬은 AI에게 막연하게 맡기는 대신, 기법이라는 규칙을 따르게 해서 결과를 일정하게 만듭니다.

## 작동 원리

핵심은 **AI가 하는 일과 스크립트가 하는 일을 나눈 것**입니다.

- **Claude가 하는 일:** 기획서를 읽고 테스트 모델을 채우고, 케이스 문장을 씁니다.
- **스크립트가 하는 일:** 경계값과 동등 분할을 계산하고, 체크리스트를 만들고, 빠진 항목을 셉니다.

AI에게 "빠진 것 없어?"라고 물으면 실행할 때마다 답이 다릅니다. 그래서 정답이 하나뿐인 계산과 세기는 스크립트가 맡습니다. 같은 테스트 모델에서는 누가 돌려도 같은 체크리스트가 나오고, 빠진 항목이 몇 개인지 숫자로 확인할 수 있습니다.

```
기획서
  ↓ 1. 사실 추출        Claude가 기획서를 읽고 test-model.json을 채웁니다
  ↓ 2. 도출             스크립트가 경계값과 분할을 계산합니다
  ↓ 3. 체크리스트       스크립트가 반드시 테스트할 항목에 ID를 붙입니다
  ↓ 4. 케이스 작성      Claude가 기법 문서를 읽고 항목별로 케이스를 씁니다
  ↓ 5. 커버리지 점검    스크립트가 빠진 항목이 0개인지 확인합니다
  ↓ 6. 검증과 내보내기  규칙의 출처를 기획서 원문과 대조하고 CSV로 내보냅니다
```

**테스트 모델**은 기획서를 테스트하기 좋게 다시 정리한 중간 문서입니다. 비즈니스 규칙(기획서 원문 인용 포함), 입력과 제약 조건, 상태와 전이, 조건 조합표, API 요건, 위험, 열린 질문을 정해진 칸에 담습니다. 예를 들어 테스트 모델에 "수량 최소 1, 최대 99"가 기록되면, 스크립트가 0, 1, 2, 98, 99, 100을 계산해 체크리스트 항목으로 만듭니다.

### 세 가지 원칙

1. **출처 없이 단정하지 않습니다.** 모든 비즈니스 규칙에 기획서 원문을 인용하고, 스크립트가 그 인용이 기획서에 실제로 있는지 대조합니다.
2. **기획서에 없는 답은 지어내지 않습니다.** 정의되지 않은 동작은 추측하지 않고 열린 질문으로 남깁니다.
3. **위험이 낮은 조합은 일부러 건너뜁니다.** 모든 조합을 나열하지 않고, 무엇을 왜 뺐는지 밝힙니다.

### 블랙박스와 화이트박스

- **블랙박스(기본):** 기획서를 보고 케이스를 만듭니다. 항상 적용합니다.
- **화이트박스(보조):** 소스 코드가 있으면 실행되지 않은 분기를 찾아 케이스를 보탭니다. 이때도 기대 결과는 코드가 아니라 기획서에서 가져옵니다.
- **경험 기반:** 실제로 나왔던 버그를 근거로, 기획서가 말하지 않는 실패를 보탭니다.

## 실제로 써 보니

QA용으로 만들었지만, 기획자가 직접 써 보니 쓰임이 더 넓었습니다.

- **놓친 기획 정의를 찾아 줍니다.** 기획서에 답이 없는 부분을 지어내지 않고 열린 질문으로 남기기 때문에, 결과를 받아 보면 "이 경우는 어떻게 처리하지?"라는 질문 목록이 먼저 나옵니다. 결정 테이블을 채우다 보면 기획서가 정하지 않은 조건 조합도 드러납니다. 테스트 전에 기획서의 빈칸을 메우는 용도로도 쓸 수 있습니다.
- **예외 사항을 많이 잡아 줍니다.** 무효 입력, 허용되지 않는 상태 전이(예: 배송 중 취소), 권한 경계, 중복 요청, 외부 서비스 장애처럼 기획서에 잘 적히지 않는 실패 경로를 기법에 따라 빠짐없이 훑습니다.

## 담긴 기법

| 분류 | 문서 |
| --- | --- |
| 명세 기반(블랙박스) | 동등 분할, 경계값 분석, 결정 테이블, 상태 전이, 조합 테스트, 유스케이스와 유저 스토리, 비즈니스 프로세스 |
| 구조 기반(화이트박스) | 코드 커버리지(구문, 분기, MC/DC) |

| 경험과 위험 | 경험 기반(오류 추정), 위험 기반 우선순위 |
| 점검 | 작성 전: 인수 기준, 보고 전: 자기 점검 |

기법 문서는 `qa-test-cases/references/techniques/`에 있습니다. 체크리스트에 해당 항목이 나올 때만 필요한 문서를 골라 읽습니다.

## 설치

`qa-test-cases` 폴더를 Claude Code 스킬 폴더에 복사합니다.

```bash
git clone https://github.com/uuuu66/qa-write-skill-istqb.git
cp -r qa-write-skill-istqb/qa-test-cases ~/.claude/skills/
```

프로젝트에서만 쓰려면 `~/.claude/skills/` 대신 프로젝트의 `.claude/skills/`에 복사합니다. claude.ai나 Claude 데스크톱 앱에서는 `qa-test-cases` 폴더를 zip으로 묶어 스킬로 업로드하면 됩니다.

스크립트는 Python 3 표준 라이브러리만 사용합니다.

## 사용

```
/qa-test-cases 기획서.md
```

"이 기획서로 테스트 케이스 만들어 줘", "TC 뽑아 줘"처럼 요청해도 됩니다. 화면 명세 같은 문서가 따로 있다면 기획서와 함께 넣으면 출처로 인정되어, 화면 문구까지 구체적인 기대 결과를 얻을 수 있습니다.

결과물:

- **열린 질문:** 기획서가 답하지 않아 테스트를 막는 질문부터 정리되어, 기획자에게 바로 보낼 수 있습니다.
- `test-model.json`: 기획서에서 뽑은 규칙, 입력 제약, 상태, 위험, 열린 질문
- `checklist.json`: 반드시 테스트할 항목 목록
- `test-cases.json`, `test-cases.csv`: 기법과 근거가 붙은 테스트 케이스
- **커버리지와 검증 결과:** 빠진 항목, 중복, 기획서에서 찾지 못한 규칙

## 스크립트만 직접 실행하기

```bash
python3 qa-test-cases/scripts/testmodel.py derive test-model.json > test-model.derived.json
python3 qa-test-cases/scripts/testmodel.py coverage test-model.derived.json > checklist.json
python3 qa-test-cases/scripts/testmodel.py coverage test-model.derived.json test-cases.json
python3 qa-test-cases/scripts/verify.py test-model.derived.json test-cases.json 기획서.md
python3 qa-test-cases/scripts/export_csv.py test-cases.json > test-cases.csv
```

## 함께 키워 가기

기법은 기획서에서 나오는 케이스를 빠짐없이 만들어 주지만, 실제로 터졌던 버그는 기획서에 없습니다. 버그를 만나거나 부족한 케이스를 발견하면 기록해 주세요. 그 기록이 유저 케이스로 쌓여 다음 테스트 케이스에 반영됩니다.
